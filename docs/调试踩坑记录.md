## 坑 1：雷达静态 TF 把 −92° 装进了 roll，而不是 yaw

**现象**
建图永远是星芒/重影，激光贴不住墙；但静止时贴图率又很高（99%），极具迷惑性。

**证据**
```bash
$ ros2 run tf2_ros tf2_echo base_link base_laser
Rotation: in RPY (radian) [0.000, 0.000, -1.606]      # ← 这是"期望"，实际当时是 roll
Rotation: in RPY (degree) [0.000, 0.000, -92.000]
```
实际日志打出的是 `rotation: ('-0.719339','0.000000','0.000000','0.694659')`，
即绕 **X 轴**（roll）−92°，不是绕 Z 轴。

量化验证（把 1995 个扫描点按当前 TF 变换到 `base_link`）：

| 使用的 TF | x 范围 | y 范围 | \|y\|<0.1m 的点 |
|---|---|---|---|
| 当前（roll −92°） | [−4.20, 1.32] | **[−0.21, 0.17]** | **1651 / 1995** |
| 正确（yaw −92°） | [−5.80, 4.82] | [−4.30, 1.46] | 34 / 1995 |

整帧扫描被压成 **0.38 m 宽的窄带**，几乎是 1 维数据，扫描匹配无从下手。

**根因**
ROS 2 `static_transform_publisher` 的位置参数顺序是：

```
x y z yaw pitch roll  frame_id child_frame_id
```

原配置 `0 0 0.18 0 0 -1.6057 base_link base_laser` 把 −1.6057 放在了第 6 位（**roll**），
而意图是"雷达安装角 yaw = −92°"。

**修复**
`firmware/../ros2_app/.../stl27l.launch.py`（见 `host_misc`）改用**新式命名参数**，消除歧义：

```python
arguments=['--x','0','--y','0','--z','0.18','--yaw','-1.6057',
           '--pitch','0','--roll','0','--frame-id','base_link','--child-frame-id','base_laser']
```

## 坑 2：雷达每帧点数不固定 → karto 直接 abort

**现象**
网页显示 "SLAM Toolbox 已退出（0）"，看起来像正常退出，其实进程是被 `SIGABRT` 杀掉的：

```
LaserRangeScan contains 2169 range readings, expected 2168
terminate called after throwing an instance of 'std::runtime_error'
  what():  Mapper FATAL ERROR - unable to get pointer in probability search!
process has died [pid 22298, exit code -6]
```

**证据**
连续采 30 帧 `/scan`，长度每帧都不同，`angle_increment` 也在变：

```
2156 2157 2159 2160 2167 2168 2169 2170 2171 2172 ...
angle_increment: 0.00289414 ~ 0.00291563
```

长时间统计：**2135 ~ 2176**（差 41 个点，约 2%）。

**根因**
STL-27L 每圈由数据包拼成，转速抖动导致每圈点数不同。karto/slam_toolbox
按**第一帧的点数**分配射线缓冲区，后续任何一帧点数不同就越界。

**修复**
新增 `web/scan_normalizer.py`：把 `/scan` 按固定角度栅格重采样成
**固定 2100 点**，发布到 `/scan_fixed`；slam 的 `scan_topic` 改为 `/scan_fixed`。

```
固定点数 2100，angle_increment = 2π/2100 = 0.002991993
最近邻分箱，保证不留空洞
```

## 坑 3：扫描里的 NaN 被 karto 当成有效读数

**现象**
坑 2 修好后仍崩，且这次是**激活后立刻**崩，没有点数告警。

**证据**
```
/scan        : 2170 点，其中 NaN 169 个（7.8%）
/scan_fixed  : 2100 点，其中 NaN 149 个   ← 归一化把 NaN 原样转发了
```

**根因**
karto 判断读数是否有效用的是 `reading <= 0 || reading > range_threshold`。
**NaN 与任何数比较都为 false**，于是 NaN 被当作"有效"，接着算栅格索引得到非法值，
`GetDataPointer()` 返回 NULL 就抛 `unable to get pointer in probability search`。

**修复**
归一化时把非有限值/非正值替换成一个**大于阈值的有限值**（`range_max`），
让 karto 按"超量程"处理：

```python
bad = ~np.isfinite(out_ranges) | (out_ranges <= 0.0)
out_ranges = np.where(bad, no_return, out_ranges)
```

## 坑 4：robot_state_publisher 启动时卡死，TF 树断成两棵

**现象**
开机后 `odom → base_laser` 解析失败：

```
Could not find a connection between 'odom' and 'base_laser'
because they are not part of the same tree. Tf has two or more unconnected trees.
```

此时 SLAM 一帧扫描都收不到，网页激光整体飞出去。

**证据**
```bash
$ ps -o pid,stat,etime,cmd -p 1049
   1049 Sl  07:23  /opt/ros/jazzy/lib/robot_state_publisher/robot_state_publisher ...
$ cat /proc/1049/wchan
futex_do_wait            # 主线程卡在互斥锁上
$ ros2 node list | grep robot_state
（无输出）              # 进程活着但没进 ROS 图
$ grep robot_state_publisher /root/chuyun_bringup.log
[robot_state_publisher-2] [INFO] ... Robot initialized   # 初始化完就卡住了
```

**根因**
启动瞬间负载过高（相机 + EKF + SLAM + agent + Web 同时起，4 核 load 9+），
`robot_state_publisher` 在 DDS 初始化阶段死锁，静态 TF 一条都没发出去。

**修复**
短期：`systemctl restart chuyun-stack`。
长期建议：给 `chuyun-watch.sh` 增加 TF 健康检查——连续多次探不到 `odom→base_laser`
就重启主栈（当前只检查 3000/8765 端口）。

**自查命令**
```bash
ros2 run tf2_ros tf2_echo odom base_laser   # 出现 "unconnected trees" 就是它
```

## 坑 5：残留的 static_transform_publisher 造成重复 TF

**现象**
改完 launch 文件重启雷达后，`tf2_echo` 仍显示旧的错误值。

**证据**
```bash
$ ps -eo pid,etimes,cmd | grep static_transform_publisher
 5621 1254  ... 0 0 0.18 0 0 -1.6057 base_link base_laser --ros-args -r __node:=...
17012   44  ... --x 0 --y 0 --z 0.18 --yaw -1.6057 ... base_link base_laser --ros-args ...
```
旧进程（roll 版）没被杀掉，和新进程（yaw 版）**同时发布同一对 frame**，
tf2 取谁看时序，结果飘忽不定。

**根因**
`ros2 launch` 主进程被杀，但它的子进程 `static_transform_publisher` 存活。
`pkill -f stl27l.launch` 只匹配得到 launch 进程。

**修复**
```bash
# 杀掉"位置参数版"的那一个，只留新式参数版
ps -eo pid,cmd | grep static_transform_publisher | grep -F '0 0 0.18 0 0 -1.6057'
kill <pid>
```
这也是改成**新式命名参数**的另一个好处：一眼能区分新旧进程。

## 坑 6：EKF 用马氏距离门限把 IMU 全拒了，yaw 冻结

**现象**
跑一段时间后地图开始糊，但车还在动。翻 bag 才发现：

```
车（雷达互相关）累计转了 +593°，EKF 的累计 yaw 一直停在 -362°（≈ -2°），600 秒没变过。
```

**证据**
把一次 15 分钟录制逐窗口对比（旋转量与雷达互相关、陀螺积分对照）：

```
 t(s)  gyro_int°  ekf_d°  wheel_d°   ekf_move  wheel_move
  108    -82.4    -82.4     +0.1     0.817 m   1.078 m   ← 修好后：完全一致
```

修复前同一份 bag：`-22° → -157°` 跳变，之后 `-0.00°/20s` 一动不动。

**根因**
`robot_localization` 默认带马氏距离门限（`imu0_twist_rejection_threshold: 10`）。
一次大跳变把状态协方差搞乱后，**之后每一帧 IMU 都被判为异常而丢弃**，yaw 状态不再更新。

**修复**
`host_ws/src/chuyun_bringup/config/ekf.yaml`：

```yaml
imu0_twist_rejection_threshold: 1.0e9
odom0_twist_rejection_threshold: 1.0e9
odom0_pose_rejection_threshold: 1.0e9
dynamic_process_noise_covariance: true
```

## 坑 7：EKF 融合轮式绝对位置 → 位置被错误的轮式 yaw 拖走

**现象**
`map→odom` 修正量高达 **1.98 m / 55.8°**，地图呈放射状。

**证据**
直接对比 `EKF` 和轮式 `/odom` 的 x,y：

```
 t(s)      EKF(x,y,yaw)            车轮(x,y,yaw)         位置差
  30   (+0.07,+1.11,-22.4°)   (+0.07,+1.11, -5.1°)   0.002 m   ← 车转了 18°
  35   (+0.08,+1.20,-31.6°)   (+0.08,+1.20, -5.3°)   0.000 m
```

**朝向**已经被陀螺纠正（−22°→−31°），但**位置和轮式里程计一模一样**（差恒为 0），
因为 `odom0_config` 里 x/y 是 true。轮式的位置是用**它自己的坏 yaw** 积分出来的，
于是"正确的朝向 + 错误的轨迹"组合，贴出来的图必然散。

**根因**
麦轮打滑时轮式 yaw 完全不可用（原地转 137°，轮式只报 −1.5°），
而它积分出的绝对位置也就跟着错。融合绝对位置等于把错误轨迹钉死。

**修复**
`ekf.yaml` 只融合**速度**，位置交给 EKF 自己用"速度 × 陀螺朝向"积分：

```yaml
odom0_config: [false,false,false,   # x y z
               false,false,false,   # roll pitch yaw
               true,  true,  false, # vx vy
               false,false,false,
               false,false,false]
imu0_config:  [... vyaw = true ...]
```

修复后 `map→odom` 修正降到 **0.13 m / 1.6°**，最终甚至到 **0.04 m / 0.0°**。

## 坑 8：网页的 `/web/tf` 从来不转发 `/tf_static`

**现象**
RViz 里激光和地图贴合良好，**网页里红点整体偏出去**一大截；但两条链路用的是同一份数据。

**证据**
前端 `SlamMap.vue` 计算雷达位姿时：

```js
let sOffset = lookupTf('base_link', scanFrame)   // 查不到 → null
sensorOffset.value = sOffset                      // 保持默认 {x:0,y:0,yaw:0}
```

于是激光被画在**少了 −92° 旋转**的位置上。而 `web_tf_aggregator.cpp` 的订阅是：

```cpp
subscription_ = create_subscription<TFMessage>("/tf", ...);   // 只有动态 TF
```

`base_link → base_laser`（−92°）和 `base_footprint → base_link` 都是**静态变换**，
只走 `/tf_static`，从头到尾就没送到浏览器。

**根因**
聚合节点漏订阅 `/tf_static`。这是**既有 bug**，只是之前地图本身就糊，看不出来。

**修复**
`web_tf_aggregator.cpp` 同时订阅 `/tf_static`（`transient_local`），
静态变换**不参与老化过滤**，并在快照里重新打时间戳：

```cpp
static_subscription_ = create_subscription<TFMessage>(
  "/tf_static", QoS(KeepLast(100)).reliable().transient_local(), ...);
```

修好后 `/web/tf` 里能看到完整的 16 个 frame。

## 坑 9：主控的 x/y/ω 符号整体与 ROS 相反

**现象**
按 `W` 车往后退；按"左转"车往右转。

**证据**
抓 `/cmd_vel_raw`：

```
按 W  → /cmd_vel_raw  vx = +0.550    ← 网页发的是标准 ROS 前进
按 S  → /cmd_vel_raw  vx = -0.550
```
而车实际往反方向走。

**根因**
固件的运动学/电机方向约定与 ROS 相反（很可能是 `kMotorSigns` 或运动学符号整体取反），
而编码器反馈也跟随同一套约定，所以**主控自己内部是自洽的，只是整个世界是镜像的**。

**修复**（三处，符号只在一层生效，避免双重取反）

| 层 | 文件 | 改动 |
|---|---|---|
| 指令 | `web/cmd_vel_shaper.py` | `AXIS_SIGN = -1.0`，输出前对 x/y/ω 整体取反 |
| 反馈 | `chuyun_bringup/src/ekf_input_adapter.cpp` | `odom_axis_sign = -1.0`，对 twist 与 pose 取反 |
| 前端 | `web/src/App.vue` | `ROT_SIGN = 1`（保持标准 ROS，不再单独取反） |

**验证**
```
发 /cmd_vel_raw vx=+0.100  →  整形输出 /cmd_vel vx=-0.100  →  车实际前进  ✅
```

> ⚠️ 做完全局符号翻转后，务必确认地图**没有左右镜像**（对照真实房间的门/家具方位）。

## 坑 10：轮速比例误差 +2.05%

**现象**
走廊这种退化方向上位置完全靠轮子，比例误差会线性累积。

**证据**
标定：地面上量 3.25 m 直线，让车走一趟（实测净转角仅 1.41°、横向偏离 4 cm，数据干净）：

```
真实距离        3.250 m
原始 vx 积分    3.3185 m
EKF vx 积分     3.3194 m
EKF 位姿位移    3.3165 m      → 多报 2.05%
```

**根因**
轮径实测值、轮胎压缩量、减速比标称值与实际值共同作用。
另外固件 `kEncoderCountsPerWheelRev = 68000`，而按手册理论值
`500 ppr × 4 × 32 = 64000`，两者差 6.25% —— 说明这个常数本身也不精确。

**修复**
不动固件，在适配器里乘一个标定系数：

```yaml
parameters: [{'odom_linear_scale': 0.980, 'odom_axis_sign': -1.0}]
```

## 坑 11：陀螺仪开机标定被污染（静止时 +16 °/s）

**现象**
"IMU 不可用"——静止时角速度不为零，积分一分钟漂几十度。

**证据**

| 轴 | 一次"脏"开机 | 一次干净开机 |
|---|---|---|
| gyro_x | −5.13 °/s | −1.11 °/s |
| gyro_y | +6.65 °/s | +1.21 °/s |
| **gyro_z** | **+16.01 °/s** | **+0.78 °/s** |

**根因**
`lsm6ds3_driver.cpp` 的 `Init()` **无条件**执行 `CalibrateGyro()`：

```cpp
WriteRegister8(kRegCtrl3C, 0x04);
CalibrateGyro();            // 约 3 秒，不判断车是否静止
```

开机那 3 秒只要有人碰车、或底盘还在晃，运动就被**永久写死**成本次运行的零偏。

**修复**
在 C++ 适配器里**运行期重估零偏**：仅当"轮速≈0 且 `/odom` 数据新鲜"持续 2 秒，
才用 EMA 更新零偏：

```
静止 28 s，/odometry/filtered 的 yaw 漂移 = -0.001°   → 0.00 °/min（修复前 47 °/min）
raw /imu gyro_z = +16.963 dps  →  /imu/ekf_input = +0.000 dps
```

> 建议固件侧也改：只在检测到静止时标定，或运行时动平衡重零偏。

## 坑 12：Python 节点烧掉 43% CPU

**现象**
`imu_bias.py`（最初的零偏校正节点）稳定占用 43% CPU，还把消息积压掉 27%。

**证据**（分段实测，同一块 4 核 ARM）

| 版本 | CPU |
|---|---|
| 只订阅 `/imu`（空回调） | 19% |
| 再订阅 `/odom` | 35% |
| 再发布 `/imu_biasfree` | 39~43% |
| **改成 C++ 后** | **11%（仅比原来多 1.2%）** |

**根因**
开销全在 **rclpy 的 Python 消息反序列化**，与本节点的逻辑无关。`/imu` 50 Hz + `/odom` 50 Hz
对 Python 来说太重。

**修复**
把零偏估计**下沉到已有的 C++ 适配器** `ekf_input_adapter.cpp`（它本来就同时订阅
`/imu` 和 `/odom`），删掉 Python 进程。净省约 30% 单核算力。

## 坑 13：走廊退化（数学限制，非 bug）

**现象**
在约 1 m 宽的走廊里来回走，地图必然张开成扇面、墙出现双线。

**证据**
- 单帧扫描：**46.2% 的回波在 0.75 m 以内**（0.33~0.75 m，覆盖近 360°），
  最小值 0.334 m ≈ 车宽的一半 ⇒ 两侧墙各距 0.33 m；
- 近距回波在不同时刻的同一束角度上**差 0.28~0.31 m、吻合率 0%** ⇒ 是真实环境，不是自遮挡；
- 走廊轴向没有几何特征 ⇒ 前后挪 10 cm，扫描几乎完全一样。

**结论**
2D 激光在"无特征方向"上是**数学退化**的：横向、朝向有约束，**沿走廊方向无约束**。
该方向只能靠轮子，而麦轮打滑。

**可行的缓解**
1. 建图时沿走廊**放几个特征物**（纸箱/水桶），建完撤掉——成本最低，效果最直接；
2. 只在有特征的区域建图（客厅等，贴图率可到 97%）；
3. 换传感器（3D 激光/视觉）或改善轮速闭环。

## 坑 14：放宽匹配搜索窗反而更糊

**现象**
为了"让匹配器能纠正更大的误差"，把
`correlation_search_space_dimension` 0.5 → **1.0**、`minimum_travel_distance` 0.5 → **0.2**、
`link_match_minimum_response_fine` 0.15 → 0.1，结果走廊**更糊**。

**根因**
走廊轴向是退化方向，把搜索窗放宽等于**鼓励匹配器沿走廊滑到一个错误但"看起来也说得通"的位置**，
反而把正确的里程计带偏。

**修复**
全部回退到 `0.5 / 0.5 / 0.15`。

> **教训：退化方向上，参数不是越激进越好；搜索窗应当收紧，让匹配器更信任里程计。**

## 坑 15：雷达支架没有刚性固定

**现象**
车静止不动，用手轻轻掰一下雷达，网页上**激光点相对墙体明显滑动**。

**影响**
`base_link → base_laser` 本来是恒定刚体变换，支架一松它就在**随时间变化**，
SLAM 却仍按固定值计算 —— 等价于每帧都注入随机的角度/位置误差。

**容差**：距离 3 m 处，1° 误差 = 5.2 cm，正好是一个栅格（0.05 m）。所以晃动必须远小于 1°。

**处理（硬件）**
1. 刚性支架，至少两点、最好三点固定，铝/钢件，不要亚克力悬臂或扎带；
2. 螺丝加弹垫或螺纹胶；
3. **线束固定且留余量**（很多"晃动"其实是线在拽雷达）；
4. 可在支架与车体间加薄橡胶垫吸高频振动，但**绝不能是软连接**；
5. 装完用力晃车体，雷达应与车体完全同步。

**修好之后必须重标外参**：`z=0.18 m`、`yaw=-92°` 很可能已经变了。

## 坑 16：`max_laser_range` 过大导致自由空间扇面

**现象**
地图被大片白色"尖刺"占满，看不见墙。

**证据**
统计 63 万个扫描点：

```
50% 的点 < 1.20 m
90% 的点 < 2.71 m
99% 的点 = 12.00 m   ← 3.8% 是"无回波"，贴在量程上限
```

karto 的模型是"射线上没有障碍 ⇒ 这一段是空闲空间"，于是每条无回波射线都会把白区刷到量程。
车一走，这些长条就以不同角度叠加——这就是"星芒"的主要成分。

**修复**
`max_laser_range`：12.0 → 8.0 → **4.5**（墙都在 3 m 内）。
另外发现一根**玻璃门**会让激光直接穿过去，关/开门会显著改变地图形态。

## 坑 18：语音模块的 udev 端口漂移，/dev/voice 根本不存在

```bash
udevadm control --reload-rules && udevadm trigger --subsystem-match=tty
```

## 坑 20：micro-ROS 会话会静默断开，表现为"命令发了但车不动"

**现象**
`/cmd_vel` 上明明有 −0.5，主控 `target_vx` 却一直是 0。
板子的 HTTP 状态页完全正常（能读到电池、WiFi、`motion.valid=true`），极具迷惑性。

**证据**
```
$ ros2 topic hz /odom
（无输出）                      ← 板子→上位机的回传没了

$ ros2 topic info /cmd_vel
Subscription count: 0           ← 主控已经不在订阅者列表里

$ ros2 node list | grep leap_ros_max
（无输出）
```

而同一时刻：
```
$ curl http://192.168.31.117/api/status
{"motion":{"valid":true,...}}   ← 这是板子本地残留的标志，不代表 ROS 会话
```

**根因**
上位机重启（或 micro-ROS agent 重启）后，板子的 micro-ROS 客户端卡在旧会话里，
**不会自动重连**。板子自身的 WiFi/HTTP 是另一条通道，所以看起来"板子好好的"。

**修复（不用断电）**
`POST /api/runtime-config` 会让固件重启 micro-ROS 传输层，返回 `{"ok":true,"restart":true}`。
**注意这个接口收的是表单，不是 JSON**（固件里用的是 `extract_form_field`）：

```bash
curl -X POST http://192.168.31.117/api/runtime-config \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'comm_mode=micro_ros&chassis_type=mecanum&microros_agent_ip=192.168.31.104&microros_agent_port=8888'
```

约 9 秒后 `/odom` 恢复，`/cmd_vel` 订阅者回到 1。

已封装为 **`/root/fix_microros.sh`**（先自检，不通才下发，再等重连）。

> 踩过的弯路：一开始用 JSON 发，返回 `invalid comm mode`（400），因为解析函数读的是表单字段。

## 坑 21：静摩擦死区——命令低于 0.4 m/s 轮子完全不转

**现象**
导航"规划出路径、也发了速度"，车纹丝不动；语音"前进"同样不动。

**证据**（直发 `/cmd_vel`，逐档测试）

| 命令 (m/s) | 板子 target | 轮速 |
|---|---|---|
| 0.10 | 100 | **0** |
| 0.20 | 200 | **0** |
| 0.30 | 300 | **0** |
| 0.40 | 400 | −58 ~ −119 mm/s |

而导航参数 `max_vx: 0.18`、语音 `linear_speed: 0.15` —— **全都落在这个死区里**。

**根因**
固件 PID 是**纯 P（`ki=0`）**。轮子打滑或卡住时，编码器读数接近目标值，
误差变小 → 输出变小 → 扭矩不够 → 更转不动，形成负反馈死锁。

**修复一：在线调 PID（不用烧录）**

固件把 PID 参数存在 NVS 里，可以通过 ROS 服务直接改：

```bash
ros2 service call /set_speed_pid leap_interfaces/srv/SetSpeedPid \
  '{kp: 12.0, ki: 1.0, kd: 0.0}'
ros2 service call /get_speed_pid leap_interfaces/srv/GetSpeedPid '{}'
```

效果（同一套硬件，只改 PID）：

| 命令 (m/s) | 改之前轮速 | 改之后轮速 | 实际速度 |
|---|---|---|---|
| 0.20 | **0** | 62.6 / 49.7 / 65.2 / 42.3 | 55 mm/s |
| 0.30 | **0** | 165.6 / 170.4 / 165.8 / 167.1 | 167 mm/s |
| 0.40 | −58 ~ −119 | 299.6 / 270.2 / 285.7 / 273.3 | 282 mm/s |

**起步门槛从 0.40 降到 0.20，命令→实际速度的效率从 35% 提到 60~70%。**

**修复二：整形节点加最小速度补偿**

```python
MIN_LINEAR = 0.42   # 非零线速度命令幅值补到这个值（保留方向）
MIN_ANGULAR = 0.55
```

避免控制器在接近目标时把速度降到推不动的区间（"发速度但不走"）。

**修复三（未做，需要烧录）**
`motion_config.h` 里 `kMotorPwmDeadband = 200 → 450`、`kMaxAccelRpmPerS = 500 → 800`，
从根本上提高低速推力。

## 坑 23：导航模式下网页显示"无地图模式"

让 `VOLATILE` 订阅者随时能拿到。实测改成 6 秒内收到 6 条。

## 坑 25：每次启动导航都要重设初始位姿

**现象**
地图正确、激光正确，但车被画在地图原点附近，和真实位置差几米。

**根因**
里程计每次重启从零开始，而地图是绝对坐标。
`map→odom` 在导航节点刚启动时是单位阵 —— 车"在地图原点"。

**修复：一键自动定位（全局扫描匹配）**

`web/auto_localize.py`：把当前一帧激光在世界系下的轮廓，
在整张保存的地图上做**粗到精**的搜索，找出让最多激光点落在墙上的位姿，
发布到 `/initialpose`。

优化前后：

| 项 | 初版 | 现在 |
|---|---|---|
| 匹配点数 | 140 | 60 |
| 粗搜索网格 | 0.2 m | 0.25 m |
| 朝向步长 | 5° (72) | 7.5° (48) |
| 计算方式 | Python 双循环 | numpy 按朝向向量化 |
| **耗时** | ~200 s | **7 s** |

实测得分 0.95~0.97（95% 以上激光点落在墙体 ±10 cm 内），解唯一。

已接入：`POST /api/auto_localize`，网页「导航控制」里新增**「一键自动定位」**按钮。

## 坑 26：多点导航的点位朝向恒为 0，每到一点就转身

**现象**

```yaml
goal_position_tolerance: 0.10    # 位置容差 10 cm（有效）

```

## 附：这套系统的"命令链路"全景（排查时的定位顺序）

```
① 发布者           ② 整形节点            ③ 主控              ④ 电机
/cmd_vel_raw  →  cmd_vel_shaper  →  /cmd_vel  →  AT8236 驱动
（网页/语音/导航）   限幅 + 符号翻转          订阅者必须是
                    最小速度补偿            leap_ros_max
                                    ↓
                              会话断了就没有订阅者  ← 坑 20
```

**"发了命令车不动"的排查顺序**：

1. `ros2 topic hz /odom` —— 有没有数据？没有是会话断了（坑 20）
2. `ros2 topic info /cmd_vel` —— Subscription count 是不是 1？
3. `ros2 topic echo /cmd_vel --once` —— 数值对不对、符号对不对（坑 22）
4. `curl board/api/status` —— `target_vx` 有没有变？变了但轮速为 0 就是死区（坑 21）
5. 命令幅值够不够大（≥0.42）？
